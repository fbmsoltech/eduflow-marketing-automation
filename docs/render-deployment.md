# Render Deployment

## Purpose

Render is the active public-demo target for EduFlow. The deployment uses one public API service,
two background workers, PostgreSQL and an external RabbitMQ broker hosted by CloudAMQP.

The repository-root `render.yaml` is a Render Blueprint. It builds the existing Dockerfile for all
three application processes and injects shared connection settings without storing credentials in
Git.

## Prerequisites

- a Render account;
- a GitHub account with access to this repository;
- a CloudAMQP instance and connection URL;
- a public GHCR package or a GHCR credential if using the prebuilt-image alternative;
- a local Node.js environment for applying Prisma migrations when the Render service has no shell
  access.

## Architecture

```txt
Internet
   |
   v
Render Web Service: eduflow-api
   |
   +--> Render PostgreSQL: eduflow-postgres
   +--> CloudAMQP: external RabbitMQ

Render Worker: eduflow-outbox-worker
   |
   +--> PostgreSQL
   +--> CloudAMQP

Render Worker: eduflow-automation-worker
   |
   +--> PostgreSQL
   +--> CloudAMQP
```

Redis is not used by the current implementation. `REDIS_URL` is intentionally omitted from the
Blueprint and remains optional for a future cache or distributed idempotency phase.

## Connect the Repository

1. Push the branch containing `render.yaml` to GitHub.
2. In the Render Dashboard, choose **New > Blueprint**.
3. Connect the GitHub repository.
4. Select the branch intended for the demo.
5. Confirm that Render detects `render.yaml` at the repository root.
6. Review every resource and plan before applying the Blueprint.
7. Enter `RABBITMQ_URL` when Render prompts for the value.
8. Add `REDIS_URL` manually only if a future Redis-backed feature requires it.

The Blueprint uses the current Render field `runtime: docker`. Older examples might use
`env: docker`; new configuration should follow the current Blueprint specification.

## Blueprint Services

| Resource                    | Type              | Command                                               |
| --------------------------- | ----------------- | ----------------------------------------------------- |
| `eduflow-api`               | Web Service       | `node dist/apps/api/main.js`                          |
| `eduflow-outbox-worker`     | Background Worker | `node dist/apps/api/workers/outbox-publisher/main.js` |
| `eduflow-automation-worker` | Background Worker | `node dist/apps/api/workers/automation/main.js`       |
| `eduflow-postgres`          | Render PostgreSQL | Managed by Render                                     |

The worker paths include `apps/api` because that is the output generated by the current TypeScript
build. Workers have no ingress and expose no public URL.

## Environment Variables

The Blueprint configures non-secret values and database references. Runtime secrets must be entered
in the Render Dashboard.

| Variable                        | Required by              | Source                                |
| ------------------------------- | ------------------------ | ------------------------------------- |
| `DATABASE_URL`                  | API and both workers     | `fromDatabase` in the Blueprint       |
| `RABBITMQ_URL`                  | API and both workers     | Secret entered during Blueprint setup |
| `REDIS_URL`                     | Future Redis integration | Optional and omitted from Blueprint   |
| `APP_PORT`                      | API                      | Blueprint value `10000`               |
| `NODE_ENV`                      | API and workers          | Blueprint value `production`          |
| `LOG_LEVEL`                     | API and workers          | Blueprint value `info`                |
| `RABBITMQ_EXCHANGE`             | API and workers          | `eduflow.events`                      |
| `RABBITMQ_EXCHANGE_TYPE`        | API and workers          | `topic`                               |
| `OUTBOX_PUBLISHER_ENABLED`      | Outbox worker            | `true`                                |
| `OUTBOX_PUBLISHER_INTERVAL_MS`  | Outbox worker            | `5000`                                |
| `OUTBOX_PUBLISH_LIMIT`          | Outbox worker            | `100`                                 |
| `AUTOMATION_WORKER_ENABLED`     | Automation worker        | `true`                                |
| `AUTOMATION_WORKER_QUEUE`       | Automation worker        | `eduflow.automation.events`           |
| `AUTOMATION_WORKER_BINDING_KEY` | Automation worker        | `lead-events.#`                       |
| `AUTOMATION_WORKER_PREFETCH`    | Automation worker        | `10`                                  |

Never commit connection URLs, passwords, tokens or copied Render environment exports.

If Redis is introduced later, add `REDIS_URL` to the affected services with `sync: false` and enter
the value only in Render secret settings.

## PostgreSQL

The Blueprint creates `eduflow-postgres` and injects its internal connection string into all
services through:

```yaml
- key: DATABASE_URL
  fromDatabase:
    name: eduflow-postgres
    property: connectionString
```

An external PostgreSQL provider can be used instead. In that case, remove the Blueprint database,
replace each `fromDatabase` block with `sync: false`, and enter the external `DATABASE_URL` as a
Render secret.

## CloudAMQP

Copy the AMQP connection URL from the CloudAMQP instance details page and enter it as
`RABBITMQ_URL`. Prefer the provider's `amqps://` URL when available. The Blueprint stores the value
on the API and references the same secret from both workers.

See [CloudAMQP](cloudamqp.md) for the setup sequence.

## Prisma Migrations

Apply only committed migrations:

```bash
npm ci
npm run prisma:generate
$env:DATABASE_URL = '<render-external-database-url>'
npm run prisma:migrate:deploy
```

On Bash:

```bash
DATABASE_URL='<render-external-database-url>' npm run prisma:migrate:deploy
```

Use the Render PostgreSQL external URL only from a trusted local or CI environment. Do not save it
in a tracked file or shell script. Do not run `prisma migrate dev` against the demo database.

The current runtime image intentionally contains only production application dependencies and
compiled output, so migrations are not run from the web-service startup command.

## Validate the Deployment

Replace `<api-url>` with the Render URL:

```bash
curl --fail-with-body https://<api-url>/health/live
curl --fail-with-body https://<api-url>/health/ready
curl --fail-with-body https://<api-url>/health
curl --fail-with-body https://<api-url>/metrics
```

Expected behavior:

- `/health/live` confirms that the API process is serving requests;
- `/health/ready` confirms PostgreSQL and RabbitMQ connectivity;
- `/health` returns the summary health response;
- `/metrics` returns Prometheus text metrics.

For a minimum asynchronous smoke test:

1. create an organization, campaign and lead through the REST API;
2. create and activate an automation flow for a supported lead event;
3. register the matching lead event;
4. inspect `/outbox/messages` until the message becomes `PUBLISHED`;
5. confirm the Automation Worker logs show message consumption;
6. verify the resulting automation execution or lead update.

## GHCR Alternative

The existing GitHub Actions workflow continues publishing the application image to GHCR. The
Blueprint builds the same Dockerfile directly from the linked repository so Render can deploy after
CI checks pass.

If a prebuilt GHCR image is preferred, create each Render service from **Existing Image**, use an
immutable version or `sha-` tag, provide a read-only registry credential for private packages, and
override the Docker command with the command listed above. Prebuilt-image services are managed
manually rather than by this repository Blueprint.

## Cost Warning

The API and PostgreSQL are declared with free plans suitable only for a portfolio demo. Render does
not provide free Background Worker instances, so both workers are declared on the smallest worker
plan and can incur charges. Review current Render pricing before applying the Blueprint.

For a no-cost demonstration, deploy only the API and temporary PostgreSQL resources publicly, keep
the workers suspended or uncreated, and demonstrate the complete asynchronous flow locally with
Docker Compose.
